**✅ 格點索引公式已定案：官方座標 + 6 種格點慣例假設全部落空後，靠

> 左下角為第一點東經117.975、北緯19.975，先依次經向遞增，再緯向遞增，
> 為TWD67經緯網格

這句話翻成公式，跟我們之前所有猜測都不一樣：

1. **起點是西南角 `(117.975, 19.975)`，不是 `parameterSet` 宣告的
   `StartPointLongitude=118`／`StartPointLatitude=20`**——兩者差了整整
   2 格（`0.025°=2×0.0125°`）。`parameterSet` 那組座標從頭到尾都不是
   陣列索引 0 的真實座標，是另一組概略宣告值，之前拿它當起點本身就是
   錯的，跟格點慣例方向猜對猜錯無關。
2. **先填滿一整排「經度」（西到東遞增）才換下一列「緯度」（南到北
   遞增）**——經度是快速變動軸，緯度是慢速變動軸。
3. **`GridDimensionY=561` 其實是經度格數，`GridDimensionX=441` 其實是
   緯度格數**——命名剛好跟「X＝經度、Y＝緯度」的直覺相反。反推地理範圍
   剛好是很乾淨的台灣周邊範圍（117.975~124.9875°E、19.975~25.4875°N），
   驗證了之前 E/F 假設「dimX＝緯度」的方向是對的，只是原本用的起點
   （118/20）差了 2 格，所以 E/F 當時測起來也還是全部落空。

正式公式：

```js
lonCol = round((lon - 117.975) / 0.0125)   // 0~560，561 格
latRow = round((lat - 19.975) / 0.0125)    // 0~440，441 格
index  = latRow * 561 + lonCol
```

**已改回正式程式**：`FB0046_GRID` 改用 `startLon=117.975`／
`startLat=19.975`／`lonCount=561`／`latCount=441`（欄位改名，不再叫
`dimX`/`dimY`，避免延續「X＝經度」的誤導），`gridIndexForCoord()` 直接用
上面公式。整套猜測期間寫的 `gridHypotheses()`／`searchNearbyValid()`／
6 組假設比對／±3格鄰近搜尋，連同對應的 debug 面板區塊，全部移除——
猜測工具的階段性任務結束，不留在正式程式碼裡增加閱讀負擔。

**端到端驗證**：直接用使用者上傳的真實 XML（`sent=2026-08-10T03:05:16`，
凌晨時段）跑過一次正式程式碼：陣列長度 247,401 完全吻合；全域有效值
24,335 格（散布在 lat 20.15~25.46°N、lon 117.975~124.975°E，涵蓋整個
網格範圍，不是集中在某個角落，排除「格點對到錯誤區域」的疑慮）；最大值
67.4mm 落在 (21.575°N, 120.4375°E)，是南部（高雄/屏東緯度）某處真實在
下雨，不是嘉義/雲林——七鄉鎮這次全部是 -99，但同一份資料裡別的地方

短時雨勢」，不是程式又錯了**。之前所有失敗案例都發生在白天／午後（

但 parsing 邏輯（`pickBestStation`／`deriveStateFromStation`）本身已經用真實
上傳檔案驗證過是對的，問題只在 fetch 階段。

**修法**：`fetchRainStations()` 改成雙路徑，標準路徑失敗（非 2xx）或成功但站
陣列是空的，都自動 fallback 到 fileapi 路徑，兩條都失敗才 throw（讓
`fetchAll()` 既有的 `.catch()` 包住，整批退回 unknown，不拖垮其他資料）。
另外補上 `?debug=weather` 的雨量站診斷區塊（原本完全沒有，是這次踩坑
的原因之一——UV／熱傷害／警特報都有診斷區塊可以現場看欄位對不對，唯獨
雨量站沒有），列出每個方向比對到哪個站、站上原始 Now/Past10Min/Past1hr
值，之後同類問題可以直接用截圖抓到，不用再靠猜。

**教訓**：這是本專案第三次因為「沒有實際驗證就假設標準路徑會通」而出包
（UVExposureLevel 欄位名稱、F-B0046/F-B0053 路徑、這次的 O-A0002-001 路徑）。
之後任何新資料集，fetch 函式一律要嘛雙路徑防呆、要嘛先有使用者截圖/檔案
確認過路徑再寫死。

### ✅ W-C0033-001 已接入：兩階段官方警特報＋CCTV 交叉驗證

**觸發背景**：中南部真實發布大雨特報事件，凸顯這個資料源的價值，同時使用者提出
關鍵疑慮——大雨特報常常涵蓋整個縣市，不代表七個鄉鎮都真的受影響，直接顯示會變成
常態性假警報，久了使用者不信任。

**實測 JSON 結構**（標準路徑 `api/v1/rest/datastore` 直接打得到，不用 fileapi
舊路徑）：

```json
{
  "success": "true",
  "result": {
    "resource_id": "W-C0033-001",
    "fields": [
      {"id":"locationName","type":"String"}, {"id":"geocode","type":"Double"},
      {"id":"language","type":"String"}, {"id":"phenomena","type":"String"},
      {"id":"significance","type":"String"}, {"id":"startTime","type":"Timestamp"},
      {"id":"endTime","type":"Timestamp"}
    ]
  },
  "records": {
    "location": [
      { "locationName": "嘉義縣", "geocode": 10010.0, "hazardConditions": { "hazards": [] } }
      // 全台 22 縣市都在同一份回應裡，只到縣市層級，不到鄉鎮
      // 實測當下全台無生效中特報，hazards 全部是空陣列——這是正常基準狀態，
      // 還沒看過 hazards 非空時的實際填值內容（phenomena/significance 的
      // 真實字串），但這兩個欄位是 API 自己宣告的（result.fields），不是猜的
    ]
  }
}
```

**設計決定：兩階段顯示，避免假警報**：

```text
W-C0033 有生效中特報（嘉義縣/雲林縣）
        ↓
   CCTV 有沒有確認？
   ├─ 沒有（dry/unknown）→ ℹ️ 淡版：「嘉義縣目前有大雨特報，建議留意天候變化」
   └─ 有（wet/raining）  → ⚠️ 強版：「嘉義縣目前有大雨特報，雨量站顯示新港已在降雨，
                                      建議延後外出」
```

（用詞：「生效中」聽起來像公文用語，改成「目前有」比較口語自然——這是
2026-08-09 真的有豪雨特報生效時，使用者看著實際畫面提出的用字回饋）

關鍵實作細節：
* `phenomena`/`significance` **直接帶 CWA 官方原文**，不猜關鍵字比對——因為
  沒看過真實填值時的字串長怎樣，這是刻意避開「猜錯關鍵字」風險的做法（跟
  UVExposureLevel 那次踩的坑不同，這次完全不需要知道具體字串內容）
* CCTV 交叉驗證有**縣市範圍限制**：只有跟該縣市底下的方向的 CCTV 狀態才會拿來
  升級，不會把嘉義縣的特報跟雲林縣方向的 CCTV 混在一起判斷（避免錯誤關聯）
* 只在看「今天」時顯示，跟 CCTV 現況確認同一種限制——切到明天視角時不顯示
  （現在生效中的特報不能拿來確認明天）

**補充（W-C0033-002 技術文件確認）**：W-C0033-001/002 涵蓋的警特報種類是
颱風警報、豪(大)雨特報、陸上強風特報、濃霧特報 4 項，不是只有大雨。因為實作
時選擇「直接帶 CWA 官方原文，不篩選特定類型」，這 4 種警特報都能直接套用同一套
邏輯，不需要另外為每種類型寫特殊處理。

**測試**：13 項單元測試（含真實回應形狀的基準狀態、淡版/強版切換、跨縣市隔離、
dry 不升級、無特報時 CCTV 也不會誤觸發）全過，重跑既有回歸測試確認無破壞。

**生產事故（真的有特報生效後才發現）：`phenomena`/`significance` 欄位猜錯位置，
「生效中」前面缺特報種類**。2026-08-09 嘉義縣/雲林縣真的發布豪雨特報，①卡片
顯示「⚠️ 嘉義縣生效中」，缺了「豪雨特報」四個字，讀起來不知道生效中的是什麼。

原因：當初只看到 `result.fields`（API 自己宣告的欄位清單）把 `phenomena`／
`significance` 列為 hazard 物件的**直接**欄位，因為那時全台無生效特報、
`hazards` 全部是空陣列，沒有真的非空物件可以核對。這次使用者用
`?debug=weather` 截圖了真實非空的 hazard 物件，實際形狀是：

```json
{
  "info": { "language": "zh-TW", "phenomena": "豪雨", "significance": "特報" },
  "validTime": { "startTime": "2026-08-09 09:11:00", "endTime": "2026-08-09 23:00:00" }
}
```

`phenomena`/`significance` 包在 `info` 底下，不是直接掛在 hazard 物件上——
`result.fields` 宣告的欄位清單跟實際回應結構對不上（CWA 開放資料常見的欄位
文件與實際回應不一致問題，不是我們猜錯，是文件本身就跟真實資料不同層級）。

**修法**：`officialAlertClause()` 改成 `alert.info?.phenomena || alert.phenomena`
這種雙層 fallback，兩種形狀都吃得到，不用等下次又換了才再踩一次。

**教訓**：`result.fields` 只保證欄位「存在」，不保證欄位在物件裡的巢狀深度——
之前的教訓都是路徑（fetch URL）猜錯，這次是回應結構（欄位巢狀層級）猜錯，
同一個「沒看過真實非空樣本就寫死」的病根，只是換了一種踩法。之後遇到「目前
沒有真實非空樣本可以核對」的欄位，要嘛加雙層 fallback、要嘛在 debug 面板
明確標註「此欄位尚未用真實非空資料驗證過」。
