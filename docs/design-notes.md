# 五、新資料層討論：體感 / 紫外線 / 活動適合度

> 這份是討論記錄的整理版，用於跨對話串交接。內容依照目前 `index.html` 的實際狀態校正過，
> 不是原始討論稿的逐字複製——原始稿裡有一段已經跟現況脫節，已在下方標注修正。

## 目標

Weather Decision Engine 已經能回答：

* 哪裡雨勢風險低
* 哪些時間需要避開

但還缺：

> 今天出去舒不舒服？

例如：

* 陰天是否比晴天適合帶小孩出門？
* 哪裡比較不曬？
* 午後是否因高溫不適合長時間戶外？

## 現況：Comfort Preference Layer 已經上線，不是候選功能

> **修正說明**：原始討論稿把這一層寫成「需要 F-B0053-007 才能做」，並在「尚未定案」
> 區塊列出體感排序優先序待確認。但這一層**已經實作、測試、commit、push 到 main**，
> 資料來源不是 F-B0053-007，而是直接從既有 F-D0047 的 `WeatherDescription` 文字關鍵字
> 抽取，拆成兩個**互相獨立**的軸（這正是取代「單軸排序」的修正版）：

* **體感軸（Thermal）**：舒適 > 一般 > 偏熱 > 悶熱 > 高溫悶熱 — 決定同風險層內的排序
* **曝曬軸（Exposure）**：陰 > 多雲 > 晴時多雲 > 晴 — 只在體感相同時當次要 tie-break，
  不直接影響排名，只決定要不要提示防曬

拆成兩軸的原因：單軸排序（陰>多雲>晴時多雲>晴>悶熱>高溫）會把「晴天但不悶熱」誤判成
跟「悶熱」一樣差，也會把「陰天但悶熱」誤判成優勢。體感／曝曬是兩個不同問題，不能合併
成一條優先序。

**顯示規則（已落實）**：不產生舒適分/體感分/總分，只有排序用的優先序 index + 一句敘述
文字。例如：

> ☁️ 今日多雲偏陰，戶外活動體感較佳
> ☀️ 天氣晴朗，午後日曬較強

**架構位置（已落實）**：

```
Weather Risk Layer (F-D0047)
        ↓
判斷風險（低風險組 / 需留意組）
        ↓
Comfort Preference Layer（體感軸 + 曝曬軸，來源＝WeatherDescription 文字）
        ↓
同風險層內排序
        ↓
Decision Explanation Layer
        ↓
行程建議
```

排序規則：風險層永遠優先（低風險 > 需留意，無論體感多好都不能蓋過風險）；同風險層內先比
體感、體感相同才比曝曬、都相同才比分數——避免「陰天舒服但正在下雨的地方排第一」。

## 候選資料（真正待討論的新東西）：F-B0053-007

### 育樂天氣預報資料－台灣各類型休閒活動景點預報資料－單車一週24小時天氣預報

**這個資料集的真正價值不是重做體感排序（那已經做完了），而是看它能不能補一個
F-D0047 完全沒有的新維度：紫外線指數。**

⚠️ **未驗證**：這個資料集 ID 目前只是網路搜尋得到的名稱猜測，還沒有實際打過 API
確認是否存在。上一輪找雷達資料時猜的 `F-B0046-001` 實測後是 `Resource not found`，
`F-B0053-007` 有同樣的風險，正式往下推進前必須先做同一套驗證：

1. 用現有 CWA API Key 直接打 `https://opendata.cwa.gov.tw/api/v1/rest/datastore/F-B0053-007?Authorization=<KEY>`
2. 確認資料集是否存在、回傳格式（JSON 欄位長怎樣）
3. 確認有沒有紫外線指數欄位，以及能不能定位到嘉義七鄉鎮（新港/溪口/民雄/朴子/北港/大林/斗南）

如果驗證後發現它其實只是「單車路線」專用預報、沒有 UV 或無法定位到鄉鎮層級，這個候選
就該直接放棄，不需要勉強套用。

## 核心定位

Comfort Preference Layer（含未來可能加入的紫外線維度）不負責回答「哪裡安全」——
那是 Weather Risk Layer 的工作，永遠不能被體感蓋過。它只回答：

> 「安全的地方裡，哪裡比較適合待久一點。」
